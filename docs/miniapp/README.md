# Telegram Mini App для всех игр — архитектура и план

Статус: M0 готов; **M1 готов** (2026-11-21): сервер, `view` всех игр, образцы `fixtures/`, dev-сервер `miniapp/dev-server.sh`; **M2 готов** (2026-11-23): каркас фронтенда `miniapp/`, приёмка — `reviews/m2-shell-2.md`; **M3 готов** (2026-11-25): экраны мемо, матрицы, поездки и дороги, приёмка — `reviews/m3-games-2.md`. Решения пользователя отмечены «(решение пользователя)».

## 1. Цель

Все игры бота (Мемо, Матрица памяти, Поездка на числах, Проложи дорогу, Морской бой с компьютером и с другом, а также путь, рекорды, друзья, настройки) доступны в Telegram Mini App. Mini App — это веб-страница внутри Telegram, где у каждой игры настоящий интерфейс: крупное поле, анимации, перетаскивание кораблей, вибрация.

Чат-бот в Telegram и бот в Max продолжают работать как сейчас.

## 2. Главные решения

| Решение | Почему |
|---|---|
| **Сервер решает, клиент красивый** (решение пользователя). Правила, уровни, очки, таймеры партии, путь и рекорды остаются в `games_core` на Python. Клиент только показывает состояние и шлёт нажатия | Одна копия правил для Max, TG-бота и Mini App, они не расходятся. Бой с другом работает между чатом и Mini App |
| Бэкенд — внутри процесса TG-бота (`sea_fight_aiogram/`), **тот же экземпляр `Manager`**, та же SQLite, `platform="tg"` | Один игрок — одни данные и одна открытая партия. Замки партий и таймеры у `Manager` уже есть |
| Клиент шлёт **те же payload'ы, что и кнопки бота** (`new:memo`, `t:<sid>:<r>:<c>`, `mpf:<код>:<r>:<c>` …) | Маршрутизацию, проверки и устаревшие нажатия не нужно писать заново |
| `Screen` получает необязательное поле **`view`** — структурное состояние игры. Чат-транспорты его не видят. Mini App рисует экраны с `view` своими компонентами, а экраны без `view` — универсальным рендером «текст + кнопки» | Всё работает с первого дня, а экраны можно заменять красивыми по одному |
| Фронтенд: **Vite + TypeScript + Preact**, без UI-фреймворков. SDK — `telegram-web-app.js` | Маленький бандл, быстро открывается в Telegram, понятный стек для исполнителя |
| Хостинг HTTPS — решаем на этапе M5 (решение пользователя) | До этого разработка идёт локально, с dev-входом без Telegram |

## 3. Схема

```
Telegram-клиент
 ├─ чат с ботом ──────── Bot API (long polling) ─┐
 └─ Mini App (WebView) ─ HTTPS ─ aiohttp ─────────┤   процесс games-tg-bot
        │  статика  GET /app/…                    │   ┌──────────────────────────┐
        │  картинки GET /img/<sha1>.jpg           ├──►│ Manager (games_core)     │
        └─ WebSocket /ws (JSON) ──────────────────┘   │  sessions, mp, notifier  │
                                                      │  Storage (SQLite)        │
                                                      └──────────────────────────┘
```

`Manager` уже умеет работать с несколькими «местами показа»: `respond(reply)` возвращает ссылку на сообщение (`msg_ref`), а таймеры правят его через `push(msg_ref, screen)`. Для Mini App местом показа становится WebSocket-соединение: `msg_ref = ("web", conn_id)`. Транспорт TG маршрутизирует `push` по типу ссылки: кортеж `(chat_id, message_id)` — правка сообщения в чате, `("web", conn_id)` — кадр в WebSocket.

## 4. Протокол WebSocket (контракт M1 ↔ M2)

Все сообщения — JSON-объекты с полем `type`. Подробности и примеры — в `tz-m1-core.md`. Здесь — то, на что опирается фронтенд.

### 4.1. Подключение
`wss://<host>/ws`. Первое сообщение клиента:
```json
{"type": "hello", "initData": "<Telegram.WebApp.initData>", "start": "mp_ABC234", "client": "1.0.0"}
```
- `start` — `Telegram.WebApp.initDataUnsafe.start_param` (ссылки `t.me/<бот>/<app>?startapp=mp_<код>` / `fr_<код>`), может отсутствовать.
- Сервер проверяет подпись `initData` (HMAC-SHA256 с ключом `HMAC("WebAppData", BOT_TOKEN)`, свежесть `auth_date` ≤ 24 ч). Не прошла — `{"type": "error", "code": "auth"}` и закрытие.
- Прошла — сервер отвечает экраном: `start` → тот же payload, что и `/start <param>` в чате (`start_payload`), иначе `menu`.
- Dev-режим (только `MINIAPP_DEV=1`, только с localhost): `{"type": "hello", "dev_user": {"id": 1, "name": "Тестер"}}`.

### 4.2. Клиент → сервер
```json
{"type": "press", "payload": "t:a1b2c3:2:4", "seq": 17}
```
`payload` — строка из `button.data` или из `view.actions`. `seq` растёт на клиенте; сервер возвращает его в ответе.

### 4.3. Сервер → клиент
```json
{"type": "screen", "seq": 17, "note": "✅ Раунд пройден",
 "screen": {"text": "<b>…</b>", "rows": [[{"text": "🏠 Меню", "data": "menu"}]],
            "image": "/img/3f2a….jpg", "view": { … } }}
```
- Ответ на `press` несёт тот же `seq`. Правка по таймеру (`push`) приходит с `seq: null`.
- `note` — всплывающее уведомление (у бота это ответ на callback). Показывать как toast на 1,5 с.
- `screen: null` с `note` — экран не меняется, только уведомление (например, «Не ваш ход!»).
- `text` — HTML в подмножестве Telegram (`<b>`, `<i>`, `<code>`, `<a href>`). Клиент санитизирует его по белому списку тегов.
- `image` — URL картинки (путь, открытка), отдаётся тем же сервером, кэшируется навсегда (имя — хэш).

```json
{"type": "notice", "screen": { … }}
```
Бот «сам пишет» игроку: соперник подключился, открытка за серию, новая локация пути, уведомление друзей. В чате это новое сообщение. В Mini App это всплывающая карточка поверх текущего экрана: кнопки карточки работают как обычные `press`, крестик закрывает её.

```json
{"type": "error", "code": "auth" | "bad_request" | "server", "message": "…"}
```

### 4.4. Переподключение
Соединение рвётся (телефон уснул, сеть). Клиент переподключается с паузой 1 → 2 → 5 с и шлёт `hello` заново без `start`. Сервер показывает меню; если у игрока идёт бой, на экране «Морской бой» есть «Вернуться к партии» (`mpb`). Партии уровней, прерванные потерей связи, закрываются так же, как в чате при уходе в меню. Исключение — «⚓ Кораблики» (`docs/boats/tz.md`): партия идёт по таймеру и без окна, поэтому `hello` посреди неё сразу возвращает текущий кадр партии.

## 5. `Screen.view` — структурное состояние (контракт M1 ↔ M3/M4)

Экраны партий несут `view`. Общая часть у всех:
```json
{"kind": "memo" | "matrix" | "tower" | "path" | "sea" | "boats",
 "actions": {"tap": "t:a1b2c3:{r}:{c}", "quit": "q:a1b2c3"},
 "title": "🃏 Мемо", "level": 5, "score": 120}
```
- `actions` — шаблоны payload'ов; клиент подставляет `{r}`, `{c}` и шлёт `press`. Клиент **никогда не собирает payload сам** из других полей.
- Остальные поля зависят от `kind`. Схема `boats` — в `docs/boats/tz.md` §6.2. Полные схемы остальных с примерами — в `tz-m1-core.md` §3, а JSON-образцы каждого состояния — в `docs/miniapp/fixtures/` (генерируются тестами M1). По образцам фронтенд разрабатывается без сервера.
- Экраны **без** `view` (меню, мастер боя, рекорды, друзья, настройки, итоги партий) рисует универсальный рендер. Итог партии по-прежнему приходит текстом с кнопками, а красивая карточка итога — задача M2.

## 8. Общие правила для исполнителей

- Язык интерфейса — русский; тексты экранов приходят с сервера. На клиенте только подписи элементов управления, которых нет в ядре (например, «Повернуть»); их список — в ТЗ.
- Комментарии в коде — по-русски, как в остальном репозитории; имена — по-английски.
- Не трогать `games_core/` и `sea_fight_aiogram/` без отдельного согласования: изменения протокола идут через Claude.
- Зависимости фронтенда — только из списка в ТЗ. Новая зависимость — вопрос, а не решение.
- Поддерживаемые экраны: ширина 320–480 px (телефон), светлая и тёмная тема Telegram (`themeParams`), `prefers-reduced-motion`.
- Каждая сдача: ветка `miniapp/<часть>`, зелёные `npm test` и `npm run e2e`, скриншоты из e2e, короткий отчёт: что сделано, что нет, отступления от ТЗ.
